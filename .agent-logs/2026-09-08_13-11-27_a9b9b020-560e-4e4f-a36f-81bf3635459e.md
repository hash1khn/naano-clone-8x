### Approach

**Register**
1. Parse JSON; require `email`, `password`, and `role` in `"brand" | "creator"`.
2. `supabase.auth.signUp({ email, password })`.
3. Insert `public.users` with `{ id: auth user id, email, role, created_at }`.
4. Return **only** `{ user: { id, email, role } }` — no `session`.

**Login**
1. Parse JSON; require `email` and `password`.
2. `supabase.auth.signInWithPassword({ email, password })` (sets auth cookies).
3. Load `role` from `public.users` by that user id.
4. Return `{ user: { id, email, role }, session }` where `session` is the Supabase session object (contract names the field, not its inner shape).

**Out of scope:** `companies` / `creator_profiles` rows, other endpoints, schema changes.

**Not in the contract:** error bodies. Invalid input / Auth failure will use HTTP 4xx and `{ error: string }` so the frontend can tell failures apart. Say if you want a different error shape.

If `auth.signUp` succeeds and `public.users` insert fails, the auth user would otherwise be stuck: same email can’t register again, and login has no `role`. Register now rolls that back.

**Rollback:** delete the auth user with the service-role admin API, then return `{ error: "Registration failed" }` (500) so they can retry. If that delete also fails, return a 500 saying the account couldn’t be rolled back. Unique-constraint `23505` is treated as already registered (409) — that auth user is **not** deleted.
